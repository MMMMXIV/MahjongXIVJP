# 0.5.3.1: Mahjong input safety investigation

## Evidence and limits

Two incidents must remain separate:

* 2026-11-24 07:03:21 JST: the uploaded appcrash log reports C0000005 in
  `Utf8String.SetString+0x23`, reached through `AgentEmj.Update+0xED6`.
  Independent parsing of the uploaded minidump confirms read access to address 0,
  RDX=0, RBX=0, and instruction bytes `80 3c 1a 00` (`cmp byte ptr [rdx+rbx],0`).
  The crash-handler log records process termination at 07:03:23 and a new session
  waiting for crashes at 07:03:24. These establish the immediate fault, not the
  origin of the null pointer or proof that MahjongXIV caused it.
* 07:05:27: the user's supplied summary describes state6 `[15,76066]`, then
  state30 slot8 ButtonClick and the end of logging. The original `dalamud(1).log`
  was not exposed among the referenced chat's accessible attachments in this
  workspace. This sequence is therefore attributed to that summary, not to an
  independent reread of that file. It is NOT the 07:03 crash dump's final action.
* The user clarifies the deal-screen symptom: Mahjong UI stopped responding,
  chat remained usable, and restarting FF14 allowed rejoining the match. This is
  a Mahjong UI progression failure, not evidence of an application-wide hang.

No native crash or live game recovery has been reproduced by the automated tests.
There is no captured hang dump for the deal-screen incident. An exact causal link
between either incident and a specific injected event remains unproven.

## Defects removed

* State6's timeout used to re-enable same-frame `[15]` + `[7]`; state28 did this
  immediately. Both raw discard paths are removed. One highlight is followed by
  at least two observations of state30, separated by 120ms. Failure to settle in
  3 seconds stops input. It never triggers a stronger fallback.
* Tile, slot, complete hand layout, and addon address identify a pending discard.
  A changed identity stops it; its target is pinned while the handshake is pending.
  It does not rerun the solver and choose a different tile between highlight and click.
* Tile events must be addon-owned ButtonClick events on visible enabled button
  components. Unknown events and foreign listeners are never used as substitutes.
  Event metadata is copied to scalars before ReceiveEvent, avoiding the previous
  dereference of the event-list pointer after native dispatch may rebuild it.
  Enter/return logs distinguish entry into native dispatch from its return.
* River lengths are monotonic within a hand. Temporary UI read shrinkage and
  recovery cannot be mistaken for a new discard and replay Pass. New-hand state2
  and reconnect reset the river history.
* Popup commands are sent at most once per observed offer. No repeated state15
  Pass, no guessed unknown-label Pass and no guessed unlabeled Tsumo option.
* Result/advance/acknowledgement injection is disabled, including the legacy
  diagnostic advance command. Use the actual Next button or the native timer.
  This avoids overlapping plugin inputs and the game's own hand-change timer.
* Complete hands and popup labels must settle for 240ms. Addon replacement,
  disappearance, mode changes and new states clear stale handshake state. An
  actionable state unresolved for 12 seconds stops auto-play with a visible reason.
  State6/28/30 transitions cannot reset the safety guard and replay a discard.
* AtkValue buffers are explicitly initialized before calling SetInt.

## Validation

`dotnet test tests/MahjongXiv.Engine.Tests/MahjongXiv.Engine.Tests.csproj -c Release`
includes deterministic protocol replay tests for state6, state28, direct state30,
same-frame suppression, timeout, stale identity, regression, reconnect/reset,
unactionable states and popup rearming. These execute the production handshake
class without native game memory. The Windows publish workflow builds the full
plugin, runs the full engine/regression suite, then packages and publishes only
after those steps succeed. Test results are retained as an Actions artifact.

The native ReceiveEvent payload and each live UI layout still require in-game
validation; ButtonClick ownership checks alone are not proof of native safety.
The change deliberately fails closed when the UI cannot be identified. This can
stop automation in an unsupported scene; it does not attempt to repair a UI that
is already wedged. Results no longer advance automatically.
